# V1.1 官方核對記錄

此次從同一份已通過 ZIP CRC 的 ARM64 程式核對，新增證據檔；沒有把尚未完成的事件引擎標記成已確認。

| 項目 | 結論與證據 |
|---|---|
| 羈絆道具是否漏進資料 | 原始野外贈禮群組已有發光蘑菇、琥珀色的蜂蜜、獵人的煙斗葉；改為獨立中文表格 |
| 羈絆識別 | 0x34b5090 要求掉落權重 >0，rewardId 的分類 helper 0x2d37114 判定類型 305 |
| 角色／神器羈絆加成合併 | 0x34b1784 取得效果 10512、10513，各以 (100+正值)/100，相乘；非正值視為 1 |
| 神器效果類型 | ArtifactTable 的 expedition_affection_drop_up 是效果 10513，initialValue=30、diffValue=0 |
| 羈絆事件增權 | 0x34b54a4 把符合條件的物品事件權重乘倍率，累計新增權重 |
| 前進事件權重轉移 | 0x34b541c 計算 1−min(max(新增羈絆權重,0),可轉移前進權重)/可轉移前進權重；分母<=0回傳1，0x34b567c套用於符合條件的事件 |
| 數量上限為零 | 0x34b0fa8先讀min/max，max<1跳到後續處理，使用min固定值；max>=1且min<=max呼叫亂數區間min至max+1，因此max含端點 |

新 affection.js 封裝已確認的合併倍率、前進權重縮放及合法數量區間，不把事件權重倍率顯示為每場最後掉率；JS目前為數學等價的double運算，未保證bit-identical float32。

### 尚未通過的串連條件

1. 地圖獎勵轉換子規則已核對與封裝；還需串接探索寶石加成、神器與活動修正，才能得到最終數量。
2. 每日鑽石與區域切換：ordinary/God鑽石分類、達上限後的重抽、區域期間與池切換須整鏈重現。
3. 動態首領與條件事件：強制事件優先、一次性狀態、secret monster、獎勵門檻與連續多掉落停止條件須接入。
4. 玩家狀態與能力來源：體力輸入、技能實際等級、神器持有/滿級及解鎖狀態須傳進事件引擎，不能只顯示在UI。
5. 整輪整合驗證：事件執行次序、隨機呼叫次序、跨輪探索與每日狀態持續；官方面板取整仍只能保留估算誤差。

因此這輪通過的是各子規則及資料依賴檢查，不是整輪官方一致性驗證。開始按鈕仍只回報配置，未產生推測掉落結果。

## 每日鑽石與持有／解鎖狀態核對

已新增 `drop-state.js` 與中文狀態預覽。預覽是「指定物品抽選已發生」的條件機率，只合併本節規則及基本重抽的羈絆群組倍率，並非整場遠征掉率，也尚未合併限定獎勵增權。分析機率以 JS double 加總，樣本／群組權重及羈絆乘法使用 float32；不是官方 seed 的逐次亂數重播。

| 規則 | 核對結果 |
|---|---|
| 一般鑽石分類 | rewardId 分類102且 rarityType<5；rarityType=5 神級不計入一般日累計 |
| 日上限快照 | Context 建立時 0x34b637c 呼叫上限判定並保存到 +0x28；getter 0x34b803c 只讀快照；登記 0x34b1d7c 僅轉交累計，未更新快照 |
| 跨過500 | 累計使用加法、不截成500；例如起始499、本輪取得10→509，本輪仍沿用未達上限狀態，下一輪開始才判定已達上限 |
| 非基本物品池 | TryRollDropInternal 0x34b0d6c：過濾參數為true時讀起始上限快照；已達上限則一般鑽石樣本權重歸零，保留神級 |

## 官方別名表抽選器與批次重建

本輪成功解出individual_(1).zip內的individual_.bundle，481711569 bytes，SHA256=9dcaa549d68f4a14ad28a672ae348ea2d6ad905e7b76a501ffdf553ef8469217，與先前來源相同；直接.bundle附件未成功落地，未以它們作為讀取來源。

lottery.js依ARM64 0x550fd88重建官方別名表：權重先float32，Sum以double累加再轉float32總和；欄機率float32(weight×n÷total)；小欄由前往後、大欄從後填入工作陣列，配對時使用官方彈出順序。殘餘欄機率保留原值，不另強制改成1；首欄原始權重為0時套用官方alias=0欄修正。

抽選0x55101dc只消耗一個NextDouble，以double乘欄數後拆整數與小數，依嚴格小於欄機率判定，否則取alias。不能使用CDF替代來要求相同亂數輸入下的相同樣本。

ChooseEventSample先完成各候選權重更新（SetWeight rebuild=false），有變更後於0x2d07090重建一次。符合條件的強制事件先選原始weight最高者，相同weight保留先出現者；存在強制事件便不重建和不消耗抽選亂數。已加入批次權重更新及強制優先接口。強制是否符合條件／一次性／checkpoint仍由外層傳入，接口不推測這些條件。

測試直接積分別名表各欄的機率總量，覆蓋零權重、極小權重、均等池及float32誤差；另外檢查指定亂數下的精確候選、批次重建及強制事件不消耗亂數。空／全零池拒絕抽選是模擬器額外保護，未宣稱官方raw alias class也拒絕。

證據：alias-build-arm64.txt、alias-sample-arm64.txt、event-lottery-rebuild-arm64.txt。完整事件handler、能力來源、條件與PRNG初始化仍待整合；沒有將新抽選器通過單元測試等同於完整官方遠征已完成。
